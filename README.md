# Добросмена — локальный тестовый кабинет

Тестовый full-stack прототип: Django + PostgreSQL + простой web UI. Три роли работают с одними данными: заказчик, исполнитель, администратор.

## Что нужно
- Windows 10/11
- Docker Desktop

## Запуск
1. Установите Docker Desktop и запустите его.
2. Откройте PowerShell в папке проекта.
3. Выполните:

```powershell
docker compose up --build
```

4. Откройте http://localhost:8000

PostgreSQL будет доступен локально на `localhost:5432`.

Параметры БД:
- БД: `dobrosmena`
- Пользователь: `dobrosmena`
- Пароль: `dobrosmena_local`
- Порт: `5432`

Остановка:
```powershell
docker compose down
```

Удалить БД и начать заново:
```powershell
docker compose down -v
docker compose up --build
```

## Что тестировать
В верхнем меню можно переключаться между тремя ролями. Это не настоящая авторизация, а режим демонстрации интерфейсов.

Сценарий:
1. Заказчик → «Создать заказ».
2. Администратор → увидеть заказ на подборе → назначить исполнителя.
3. Исполнитель → «Я прибыл / начать».
4. Исполнитель → «Завершить» → «Отчёт».
5. Заказчик/администратор → увидеть обновлённый статус.
6. Заказчик → «Запросить замену»; администратор увидит состояние `Замена`.

## Архитектура данных
Основная СУБД — PostgreSQL. Django ORM является единственным источником бизнес-логики работы с БД. В моделях уже предусмотрены User, Recipient, CarePlan, Order, ShiftReport, Incident и AuditLog.

Это демонстрационный стенд, а не production: пока нет реальной авторизации, SMS, платежного шлюза, загрузки документов, объектного хранилища, полноценного RBAC и юридически значимого аудита.


## Кабинеты MVP

Тестовый стенд содержит три связанных кабинета: заказчик, исполнитель и администратор. Все они читают одну PostgreSQL БД.

### Сценарий проверки
1. Откройте кабинет **Заказчика** → «Мои заказы» → создайте новый заказ.
2. Переключитесь на **Администратора** → «Подбор» → назначьте исполнителя.
3. Переключитесь на **Исполнителя** → «Предложения»/«Мои смены» → начните смену.
4. Создайте отчёт.
5. Вернитесь к **Заказчику** и откройте заказ.
6. В админке проверьте «Инциденты», «Финансы» и «Аудит».

## Подключение к PostgreSQL

## Этап 1–3: настоящая авторизация и API v1

В этой версии демо-переключатель ролей заменён серверной авторизацией.

### Тестовые аккаунты

Пароль всех демонстрационных аккаунтов:

`Dobrosmena123!`

- Заказчик: `+7 900 000-00-02`
- Исполнитель: `+7 900 000-00-03`
- Администратор: `+7 900 000-00-01`

Регистрация из интерфейса доступна для ролей `Заказчик` и `Исполнитель`. Создать администратора через публичную регистрацию нельзя.

### Новый API

- `POST /api/v1/auth/register/` — регистрация
- `POST /api/v1/auth/login/` — вход
- `POST /api/v1/auth/logout/` — выход
- `GET /api/v1/auth/me/` — текущий пользователь
- `GET /api/v1/bootstrap/` — данные кабинета с серверной фильтрацией по роли
- `POST /api/v1/orders/` — создать заказ (только заказчик)
- `POST /api/v1/orders/<id>/assign/` — назначить исполнителя (только администратор)
- `POST /api/v1/orders/<id>/accept/` — принять назначенную смену (только исполнитель)
- `POST /api/v1/orders/<id>/start/` — начать смену (исполнитель)
- `POST /api/v1/orders/<id>/complete/` — завершить смену (исполнитель)
- `POST /api/v1/orders/<id>/report/` — отчёт по смене (исполнитель)
- `POST /api/v1/orders/<id>/replace/` — запросить замену (участник заказа/администратор)
- `POST /api/v1/incidents/<id>/resolve/` — закрыть/открыть инцидент (администратор)

Авторизация API выполняется через заголовок:

`Authorization: Bearer <token>`

### Что изменилось в модели заказа

Добавлены состояния, необходимые для будущей полноценной state machine:

`draft → risk_check → matching → caregiver_requested → accepted → payment_authorized → confirmed → en_route → arrived → started → completed → customer_confirmed → settlement`

Также предусмотрены `replacement`, `incident`, `disputed`, `cancelled`, `blocked`.

### Защита от двойного бронирования

При назначении и принятии смены backend проверяет пересечение интервалов времени. Проверка выполняется внутри `transaction.atomic()` с блокировкой заказа, поэтому два параллельных действия не должны пройти обычной проверкой одновременно.

Это ещё не финальная production-реализация slot-locking/PostgreSQL exclusion constraint; она относится к следующему техническому этапу.

### Как проверить новую версию

1. Запустите Docker Desktop.
2. В папке `dobrosmena-local` выполните `./start.ps1`.
3. Откройте `http://localhost:8000`.
4. Войдите одним из тестовых аккаунтов.
5. Выйдите и войдите другим аккаунтом — кабинет и доступные действия изменятся согласно роли.
6. Проверьте, что попытка вызвать административный endpoint с аккаунта заказчика получает HTTP 403.
7. Создайте заказ как заказчик.
8. Назначьте исполнителя как администратор.
9. Примите и начните смену как исполнитель.

### Важно

Это всё ещё локальный технический MVP. Токен хранится в `sessionStorage` только для удобства локального прототипа. Для production необходимо перейти на более строгую схему с безопасными cookie/сессиями, CSRF-защитой, HTTPS, ограничением попыток входа, подтверждением телефона, секретами вне репозитория и полноценной моделью управления сессиями.

## v1.2 — регистрация и восстановление аккаунта

В этой версии добавлен пользовательский сценарий авторизации:

- регистрация с выбором роли: Заказчик или Исполнитель;
- обязательные поля: ФИО, номер телефона, e-mail, пароль;
- телефон нормализуется для проверки совпадений;
- e-mail сравнивается без учёта регистра и пробелов;
- при совпадении телефона или e-mail регистрация блокируется и показывается всплывающее окно;
- вход выполняется по телефону ИЛИ e-mail + пароль;
- при неверном пароле открывается сценарий восстановления аккаунта;
- endpoint `POST /api/v1/auth/recover/` пока только принимает запрос и показывает информационное сообщение;
- отправка одноразового кода на телефон/e-mail будет подключена отдельным этапом.

Важно: текущая версия не отправляет реальные SMS/e-mail и не меняет пароль через код восстановления. Это следующий этап.

## Администратор v1.3

Административный кабинет доступен только пользователю с ролью `admin`.

Демо-администратор:
- Телефон: `+7 900 000-00-01`
- Пароль: `Dobrosmena123!`

В разделе «Пользователи» администратор видит:
- количество заказчиков, исполнителей и администраторов;
- ФИО, телефон и e-mail;
- роль пользователя;
- дату регистрации;
- дату последнего входа;
- активность и статус проверки;
- карточку пользователя;
- связанных получателей;
- заказы заказчика или смены исполнителя;
- завершённые и активные заказы;
- журнал действий пользователя.

Пароли, токены авторизации и иные секреты администраторам не показываются.

Новый endpoint:
`GET /api/v1/admin/users/<id>/` — только для роли `admin`.


## v1.4 — исправления регистрации и входа

- ФИО хранится отдельными полями `last_name`, `first_name`, `middle_name`; `full_name` сохраняется как производное отображение.
- Телефон хранится в едином отображаемом формате `+7 900-000-00-00`; при входе формат ввода нормализуется, поэтому вход работает с пробелами, дефисами и без них.
- При регистрации проверяется совпадение телефона и e-mail с существующими аккаунтами.
- При неверном пароле на форме входа показывается сообщение «Неверный пароль» и доступна ссылка «Забыли пароль?».
- Восстановление пока является заглушкой: реальная отправка одноразового кода на телефон/e-mail будет подключена позже.
- Демо-администратор: телефон `+7 900-000-00-01`, e-mail `admin@dobrosmena.local`, пароль `Dobrosmena123!`.
